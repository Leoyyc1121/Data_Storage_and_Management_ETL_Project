## 必须优先解决的缺项

### 独立人工评估没有完成

要求文档第 10 节明确要求电影和人物各至少 100 对独立人工标注，同时包含应合并和不应合并的样本、困难案例、抽样方法、标注证据和分歧处理。还要求报告自动合并 Precision、Recall、F1，以及错误合并、漏合并和人工复核覆盖。

当前两类各 120 对“来源证据标注”不能替代这一要求。现有来源对照中，电影 120 对只有 7 对能够和双方单作品映射直接比较，且均为负类；P/R/F1 为 NULL。人物来源一致性 F1 约 0.9828，但标签与系统共享来源，报告也明确说明它不是独立人工准确率。

改进方案：

1. 冻结待评估模型、规则和数据版本，先检查现有盲化保留集的适用性、来源充分性和与开发样本的隔离。
2. 由真人独立完成标注；保留理由、证据及分歧裁定。两类各取得至少 100 对可用于判断同一或不同实体的标签，证据不足单列。
3. 当前电影包适用覆盖不足，不能仅补填姓名或时间。若证据不足导致不足 100 对，应先制定并登记新的抽样方案，版本化扩展保留集；不能按模型表现挑选替代样本或把开发案例移入测试集。
4. 使用现有 `evaluate_task4.py` 和 `evaluate_people.py` 计算混淆矩阵及指标，保存错误案例、人工复核覆盖、未解决率和簇级复查结果。没有观察到某种错误时应如实报告 0，不虚构案例。
5. 新标签如被用于调参，须保留新的独立评估集再评估。

验收条件：两个独立样本均满足数量、类别、困难案例和隔离要求；指标及错误分析绑定到当前最终模型。文档没有要求正负类严格各占 50%，也没有规定必须公开标注者全名；现有脚本的身份和时间字段是项目选择的追溯方式，不能误称为课程原文逐字段要求。

证据：[人工评估说明](人工评估与剩余验收.md)、[来源对照报告](../reports/final/source_annotation_agreement.json)。

### 剪辑版本与原名没有贯通目标字段

要求文档第 5 节要求结构化版本信息包含 cut，并保留原始标题、别名和语言信息。当前存在两条具体缺口：

- `classify_products.py` 声明了 `cut`，但没有实际提取；`select_fields.py` 的 editions 表和最终选择循环不包含该字段；覆盖率也不统计它。实查目标库的 cut 断言和选择均为 0。作品合并阶段已有 169 个商品的 `variants` 提示，说明部分版本信息已被识别，却没有形成统一最终字段及缺失原因。
- IMDb 候选目录已保存 `original_title`，282 个匹配作品中 35 个原名与主要标题不同，但目标库没有 `original_title` 的字段断言或选择。原始 TSV 仍保留，信息未被彻底删除；缺口是规范字段、来源链及覆盖统计没有贯通。

改进方案：新增可追溯的 `product.cut` 与 `movie.original_title` 字段，保留原文、规范值、来源定位、规则、状态和选择理由；必要时将多语言别名另建成员表。将导演剪辑、加长、未分级等剪辑信息与修复、彩色化等其他版本属性区分，避免把所有 variants 都直接等同于 cut。来源未明确时记录 NULL 和原因。

修改抽取、字段选择、目标模型、字典、查询及覆盖率后，使用新版本目录重算受影响下游，保留旧版。验收至少包含一个有剪辑证据的商品、一个无证据商品、一个原名不同的作品，并检查最终值到原件的追溯。

代码位置：[字段选择](../src/transform/select_fields.py#L28)、[选择字段清单](../src/transform/select_fields.py#L77)、[覆盖率](../src/quality/field_completeness.py#L26)。

### 原始压缩件及下载证据不完整

任务 1 要求登记下载来源、时间、大小、SHA-256 和解析版本。当前约 9.33 GB 解压文件的大小及 SHA 已登记，也保留了用户报告的下载日期；但 `archive_file=null`、`archive_to_text_verified=false`、`downloaded_at=null`，尚不能核验最初压缩文件到当前文本的关系。

优先查找原压缩文件、下载记录及备份，登记可证明的信息，并通过流式解压哈希核对是否与现有 movies.txt 一致。找不到历史原件时，可另行获取并登记一份新的输入进行验证；必须使用真实的新时间，不能冒充原下载记录。仅重新下载并不能自动消除旧运行的历史证据缺口，应在新版本复现或由课程方接受已披露的例外。

证据：[来源登记](../reports/task1/source_manifest.reported.json)。

## 需要修正的工程与验收问题

### HTML 成功后的处理路径不完整

`classify_products.py` 第 260—261 行在发现成功网页时主动报错，明确要求先添加 HTML adapter。因而目前 JSON 替代来源路径能够运行，但爬到合法页面或导入授权快照后，不能直接完成分类及下游。

这不是“HTML 成功 0 所以课程不合格”：要求文档第 3 节允许访问受限时采用许可来源。它是一个具体能力边界，应在说明中写清楚。若要补全网页路径，应添加 HTML 到统一字段候选的适配器，保留模板、ASIN 校验、字段定位、快照哈希和解析失败原因，并将其接入 DAG。用有合法来源的快照完成端到端验证；合成 HTML 只用于单元测试，不能计作真实采集成果。

代码证据：[HTML 路径阻断](../src/transform/classify_products.py#L260)。

### 严格审计总结果被写死

`audit_requirements.py` 第 58 行无条件写入 `status='not_fully_met'` 和 `strict_assignment_acceptance=False`，部分分项通过状态也直接写成常量。当前不通过结论有真实缺项支持，但脚本本身不能可靠地证明未来已全部满足：即使补齐标签，严格模式仍固定失败。

应将要求逐项映射为动态检查，分别表示通过、失败、证据不足和适用例外；总体结果由必要项汇总。核验报告还应绑定当前输入、规则、标签和模型指纹，拒绝使用旧版本通过报告。加入“真实缺项导致失败”“证据完整时可以通过”“证据过期时失败”的逻辑测试。补齐字段之前，不应仅通过修改总状态实现所谓达标。

代码证据：[严格审计](../src/quality/audit_requirements.py#L58)。

当前数据覆盖表现需要如实保留：

| 指标 | 当前值 | 含义 |
| --- | ---: | --- |
| 商品研究元数据覆盖 | 73,813 / 253,059，29.17% | 不能当成网页成功率 |
| 待确认商品 | 245,615 / 253,059，97.06% | 完成处理状态不等于识别完成 |
| 分类为电影的商品 | 3,617 / 253,059，1.43% | 属于规则结果 |
| 多字段身份确认作品 | 282 / 3,613，7.81% | 3,613 包含未确认作品记录 |
| 映射到上述确认作品的商品 | 286 / 253,059，0.113% | 反映全商品范围识别覆盖 |
| 已确认作品的明确主演覆盖 | 96 / 282，34.04% | 部分 cast 不能冒称明确主演 |
| 完整上映日期 | 0 | 文档允许只知年份或保留缺失 |

这些覆盖率很低，会限制项目的实际整合效果；但要求文档没有规定必须达到某个元数据覆盖百分比。改进时应先分析“已取得元数据但仍无法分类”的原因、字段提取失败和作品候选阻塞漏召回，再增加许可来源；不能仅降低合并阈值来做高覆盖率。

现有 5 对人物同名分离案例有不同外部 ID、出生年和作品信用证据，但不全属于最终加载人物。课程原文没有要求这 5 对必须全部出现在最终库，因此不能仅据此断言案例数不达标；建议增加案例对应的系统决定、person_id 或明确的拒绝/待确认状态，现场能够展示系统为何保持分离。

固定离线包已有访问失败、合集、缺失日期、跨版本和人物别名等原件；冲突案例主要是内外 ASIN 冲突。如果演示第 7 项字段冲突选择，建议另提供真实的字段候选分歧及其选择或未解决结果；无法取得时明确区分来源身份冲突与同语义字段冲突，不把合成测试当实际原件。

报告已说明用户与 Codex 的工作范围，但没有其他团队成员的真实贡献记录。本次无法验证成员是否都能解释实现、规则和错误案例。按实际课程组织补充真实分工和现场演示；文档中的 3—4 人、10—15 分钟属于建议，不能自行升级为硬性人数或时长限制。

## 建议实施顺序与完成标准

| 优先级 | 工作 | 完成标准 |
