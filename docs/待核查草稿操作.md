# 逐对核查：填写位置与方法

本说明保留为可选的人工复核流程。用户已改为要求不含姓名/标注时间的来源证据标注，当前最终入口见[最终交付说明](最终交付说明.md)；不必继续填写本草稿才能使用最终交付。

电影和人物各准备 120 对候选判断。姓名、时间、身份字段均为 `null`，`reviewed` 全部为 `false`；每对不额外添加“AI辅助”标签。候选不是已经完成的人工标签，生成过程在根目录统一实施记录中保留。

## 去哪里看、哪里填

本机项目根目录下的 `data/evaluation/review_draft_v1/`：

| 文件 | 用途 |
| --- | --- |
| `movies.review.md` | 阅读电影左右两侧原始证据、候选结论和理由 |
| `movies.review.json` | 逐对填写电影核查结果 |
| `people.review.md` | 阅读人物原始演职员信用、来源姓名/年份及候选理由 |
| `people.review.json` | 逐对填写人物核查结果 |
| `evidence.json` | 保留商品原始记录、原始 TSV、来源位置和 SHA-256，不需编辑 |
| `decisions.json` | 生成这批草稿时使用的候选理由，不需编辑 |

`.md` 与 `.json` 用相同的 `number` 和 `pair_id` 对应。先看 Markdown 中该编号的左右证据，再在 JSON 的 `items` 中找到该编号。JSON 中可直接搜索 `"number": 1,` 等内容；不要修改 `pair_id`、左右原始上下文或来源登记。

原件可包含重复营销文案和错误事实。证据卡的商品正文只去除了 HTML 排版，完整原件仍在 `evidence.json`。人物原始 IMDb 人物号是来源档案信息，不是本项目人物合并预测；同一档案信用重复出现不能当作两份独立证明。

## 每一对如何填写

1. 对照左右侧的剧情、主创、年代、角色和收录集号，而非只看标题或姓氏。核查候选理由是否确实能由所列原件支持。
2. 必要时修改 `label`、`rationale` 和 `labeling_evidence`。若另查了资料，在 `labeling_evidence` 追加实际 URL/本地原件位置及所支持的事实；原有来源引用不要随意删掉。
3. 实际核查完这一对后，才把 `reviewed` 改为 `true`，把 `labeler_type` 改为 `"human"`，填写真实核查人 `labeled_by` 和实际核查时间 `labeled_at`。
4. 保存 JSON。字符串要用英文双引号，日期时间要包含时区，不要在 JSON 中加入注释或末尾多余逗号。

字段含义：

| 字段 | 填写规则 |
| --- | --- |
| `label`（电影） | `same_work` 同一作品；`different_work` 不同作品；`unresolved` 暂无法判断 |
| `label`（人物） | `same_person` 同一人物；`different_person` 不同人物；`unresolved` 暂无法判断 |
| `rationale` | 你核查后认可或修改的具体理由，不能只写“同意” |
| `labeling_evidence` | 支持实际决定的原件引用及新增证据 |
| `reviewed` | 核查前 `false`；核查完成后 `true`，是布尔值，不加引号 |
| `labeler_type` | 核查前 `null`；真实人工核查后 `"human"` |
| `labeled_by` | 核查前 `null`；核查后写本人真实姓名或课程认可的实际身份标识 |
| `labeled_at` | 核查前 `null`；核查后写实际时间，例如日期后接 `T`、时分秒及 `+08:00` |

时间格式为 `YYYY-MM-DDTHH:MM:SS+08:00`（这是格式说明，不要将这串占位文字填进文件）。不要把草稿生成时间写成人工核查时间，也不要未核查就统一批量填姓名和时间。核查过但仍无法确定的，可以保留 `unresolved` 并写明原因；这会计入“已核查但未解决”，不计入确定标签数量。

电影第一对、人物第 017/048/054 对等因材料不足保留待确认；人物第 090 对还存在“把参照影片演员当作本商品演员”的抽取风险。请优先查看各对理由中的具体缺口，而非为凑数直接接受所有候选。

## 检查有没有漏填

在项目根目录运行，只读取文件，不修改你的核查结果：

```powershell
& .\.venv\Scripts\python.exe -B src/quality/prepare_review_drafts.py check
```

输出的 `pending` 为未核查数量，`human_determinate` 为填写完整的确定判断数量，`human_unresolved` 为人工核查后仍不能判定的数量；`problems` 给出姓名/时区等漏填或格式错误的编号。这个检查只能验证填写声明和格式，不能证明已经真正核查。

本批初始候选分布：电影同一作品 14、不同作品 57、待确认 49；人物同一人物 59、不同人物 57、待确认 4。电影只有 71 对给出确定候选，因此即使全部照单接受也不足以满足至少 100 对确定标签，需要为待确认项补足真实证据。不能自行换掉登记保留对来凑数；改变样本需另有合规评估协议并重新登记绑定。

## 与正式评估的区别

课程要求的各至少 100 对**独立人工标注**仍未完成。`data/evaluation/annotation_v2/` 中绑定当前模型的正式盲化包完全未改动，仍可用于独立、未看候选结论的标注流程。

本批文件明确使用 `items` 与 `source-review-draft-v1` 格式，不能直接传给 `evaluate_task4.py` 或 `evaluate_people.py`，也不会自动改写正式评估包、准确率、目标数据库或严格验收状态。看过候选再核查属于候选可见复核，不等同于独立盲标。你填完后应保留实际协议，再整理成相应复核记录；若课程必须独立盲标，需另由未接触候选判断的人使用正式盲化包完成，不能仅改一个身份字段冒充。

这些来源摘录、逐对判断及你之后填写的身份信息保存在本机，不进入公开 Git；公开交付只保留程序、操作说明和不含逐对原件/个人姓名的汇总。
